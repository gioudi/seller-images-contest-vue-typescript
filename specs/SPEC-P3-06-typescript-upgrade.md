## 1. Context

Our TypeScript is **~4.5.5** — it shipped with the original Vue CLI scaffold and is now four major versions behind (4.5 → 5.9). It is the last really old tool in the stack now that Pinia (SPEC-P2-01), Vite (SPEC-P2-02), SCSS 7-1 (SPEC-P3-03) and lazy loading (SPEC-P3-04) are done. The ADS Phase-3 checklist explicitly lists "Upgrade TypeScript to 5.x" as a Quality & DX item.

In practice the upgrade is low-risk for the app itself because:

- **The build does NOT type-check.** Vite strips types with esbuild; neither `npm run build` nor `npm run test:unit` runs the TypeScript compiler. So a newer compiler cannot break a build's type-check phase that doesn't exist.
- **Linting is syntax-only.** ESLint uses `@typescript-eslint/parser` **without** `parserOptions.project` — it parses syntax; it does not do type-aware linting (that arrives with EST-L11). Empirically the gate stays green.
- **`skipLibCheck: true`** is set, so third-party `.d.ts` files aren't deep-checked.

What the upgrade buys us: a supported compiler for today's tooling, future-proofing for `typescript-eslint` 6/7/8 (which require TS ≥ 5.1+), access to TS 5 features, and consistency with Vite 8 / Vue 3.5. The change is one line in `package.json` plus the lockfile; nothing else needs to change.

## 2. Topic & Scope

- **Topic:** bump the `typescript` devDependency to the latest 5.x and prove the whole existing gate still passes.

**In scope:**
- `package.json` — `typescript`: `~4.5.5` → `^5.9.3`
- `package-lock.json` — regenerated by the install
- `specs/SPEC-P3-06-typescript-upgrade.md` and `CHANGELOG-PROPOSALS.md`
- Verification: `npm run lint`, `npm run test:unit`, `npm run build` all green

**Out of scope (forbidden in this branch):**
- Any change to `tsconfig.json` settings (module resolution, `verbatimModuleSyntax`, etc.) — own PR
- Adding `vue-tsc` / a `type-check` script — own PR (see §6)
- Upgrading `@typescript-eslint/*`, ESLint or Prettier — this is **EST-L11**, its own spec and PR
- Fixing pre-existing type errors in the codebase (they are not caused by this upgrade)
- Any `.vue`, `.ts`, `.js` or `.scss` source change

## 3. Design Patterns

| Pattern | Where applied | Why this pattern |
|---------|---------------|------------------|
| Dependency version bump (semver-driven toolchain refresh) | `package.json`, `package-lock.json` | the only semantic change is which compiler `@typescript-eslint/parser`, vite/esbuild and vitest consume; no application code touches TypeScript APIs directly |
| Green-gate verification (empirical acceptance, not just intent) | lint + test:unit + build | proves the compiler swap changes nothing observable before merging |

No structural or algorithmic patterns apply — this is a toolchain version change.

## 4. SOLID

- **S** — Single Responsibility: the change touches one thing (compiler version) and one concern (toolchain currency).
- **O** — Open/Closed: application code is untouched; the codebase stays open for the EST-L11 lint upgrade without modification.
- **L** — Liskov: n/a — no subtype relationships.
- **I** — Interface Segregation: n/a — no interfaces introduced.
- **D** — Dependency Inversion: the compiler is an external tool consumed through package.json only — the app code never depends on a compiler API.

## 5. Architecture & Why

```
Toolchain layer:           Owned by:          File:
TypeScript compiler 5.9    package.json       declared as devDependency only
ESLint + parser (5.x)      untouched (EST-L11)  parses syntax only, no type-aware rules
Vite / esbuild             untouched            strips types at build; no type-check
vitest / jsdom             untouched            test runtime; types stripped same way
```

Why this shape: TypeScript is a **developer-time tool**. Our runtime never sees TS — Vite compiles everything to plain JS before it ships. So the correct place for this change is the devDependency entry, and the correct proof is that the entire existing toolchain (lint → test → build) still behaves identically. A larger tsconfig modernization deliberately waits for its own PR so this one stays reviewable in a few minutes.

## 6. Future Avoid

- [ ] Never upgrade TypeScript and lint tooling in the same PR — compiler and `typescript-eslint` have coupled version support; EST-L11 handles the lint side
- [ ] Never add `vue-tsc` / enforce `tsc --noEmit` in CI until the pre-existing test/config type errors (§1 note) are fixed in their own PR — otherwise the gate is red from day one
- [ ] Never loosen strictness to silence post-upgrade errors — strict mode stays on
- [ ] No new `any` to dodge compiler complaints — banned per governance
- [ ] Do not chase the very latest nightly/major (5.x line is the target; no 6.x/7.x without its own spec)

## 8. Risks & Mitigation

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| `@typescript-eslint/*` 5.62 warns/errors on TS 5.9 | Medium | Low | empirically verified this branch: lint is green with no warnings; if it ever degrades, EST-L11 (lint upgrade) is the scheduled fix |
| New TS 5 type errors surface when someone later adds type-checking | High | Low | proven pre-existing (4 errors already present at 4.5 too, in test files); documented here and in §6 as a separate PR |
| Some transitive dependency pins a TS major | Low | Low | `skipLibCheck` + single root dedupe verified via `npm ls typescript` |
| Lockfile churn hides unrelated updates | Low | Low | only `typescript` entry changes top-level; npm reported exactly one package changed |

## 9. Testing Strategy

- Gate: `npm run lint` + `npm run test:unit` + `npm run build`
- Diagnostic (non-gating, for the record): `npx tsc --noEmit` reports only the same 4 pre-existing test/config type errors — confirms the upgrade introduces zero new type errors
- Manual smoke: `npm run dev` opens and behaves as before
